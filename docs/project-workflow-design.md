# 项目工作流产品与技术设计

> **状态：规划，新增能力尚未实现。** 本文定义后续研发的产品行为与技术边界，不代表当前安装包已有项目工作台、编码代理或自动重建入口。现有能力与新增能力在下文分别标明。实施顺序见[项目工作流实施计划](project-workflow-plan.md)，验收要求见[项目工作流验收矩阵](project-workflow-acceptance.md)。

## 1. 产品目标与范围

Tekvro 将在现有分析内核之上，增加围绕一个明确目标持续工作的项目层。一个项目保留输入身份、研究结论、证据、需要满足的要求、生成产物、检查结果及未解决问题，使 CLI、MCP 和后续本地界面能够继续同一项工作。

项目支持两类目标：

| 目标                  | 用户希望获得的结果                                       | 计划中的工作路径                       | 完成边界                                             |
| --------------------- | -------------------------------------------------------- | -------------------------------------- | ---------------------------------------------------- |
| 理解软件 `understand` | 对选定功能、文件、协议或运行现象给出可追溯的解释         | 研究、组织证据、检查结论、交付报告     | 交付过程可以完成；没有取得证据的事实仍为未知         |
| 重建软件 `rebuild`    | 在选定范围内实现可运行的软件或功能，并说明与原目标的差异 | 研究、形成要求、实现、检查、返修、交付 | 只有当前产物满足当前必需要求，才可宣告该范围验收通过 |

“理解软件”不隐含执行目标、生成代码或安装依赖。“重建软件”须保留用户指定的技术栈、目标范围和输出位置；已有项目继续修改与新建项目分别记录，不能静默把现有目录当作可覆盖的输出。

第一条完整路径聚焦具有可分发样例的网页与 H5：以现有浏览器、JavaScript、截图、网络证据和比较能力组成可重复的端到端流程。桌面应用、原生程序和游戏采用相同项目模型，但只能在对应真实宿主与验证器通过后声明支持。一个路径的成功不外推为任意软件可重建。

本设计保留 ESM TypeScript 内核、分层架构、现有提供者与命令兼容性。项目层不引入通用工作流语言、任意节点执行器或只有计划没有执行的另一套工具。

## 3. 用户体验

### 3.1 项目建立

项目输入包括目标类型、用户问题或交付目标、已选择的输入、范围、输出位置，以及适用时的技术栈和验证场景。目标可以来自用户选定的本地文件、目录、已存在的 Evidence 或明确的浏览器目标。现有工具的输入规则决定其可用性；项目层不能自行扩展目标范围。

创建后先展示已识别事实与限制：目标身份、可用分析方式、当前宿主能够执行的检查、缺少的依赖，以及可交付的最小范围。只有会改变目标含义、产物归属或执行范围的缺失信息才进入待回答项。已有请求已经表达的操作意图不再要求重复确认。

对于已有代码目录，计划支持独立工作副本或用户明确选择的就地编辑。记录起始文件身份、Git 提交和已有未提交修改；未知或并发修改必须保留。自动恢复只回滚本次运行可证明拥有的修改，不能使用清空目录或强制重置来处理冲突。

### 3.2 普通项目视图

普通视图以用户目标为中心，计划展示：

- 项目名称、范围、目标软件与当前产物版本。
- 当前阶段、已完成的实际工作、最近活动时间和耗时；没有可靠总工作量时不显示虚构百分比。
- 当前结论、证据入口、仍需回答的问题及下一步可执行动作。
- 各项要求的通过、失败、未知状态；截图、行为和构建结果分别显示。
- 产物的可打开、已启动、可运行观测，以及与验收结论分开的结果标签。
- 暂停原因、恢复条件、执行预算与已发生的可观测消耗。
- 打开报告、查看差异、继续工作、检查当前产物、暂停、取消和导出当前成果等操作。

问答与修改是不同意图。对当前结论的追问只读取已有材料或执行明确请求的分析；请求修改才进入 Builder。运行中的补充要求先形成带版本的待处理变更，在安全边界更新范围，不直接改写正在验证的要求快照。

### 3.3 专业视图

专业视图计划开放同一项目的证据、结构图、来源位置、输入与产物摘要、要求账本、检查明细、覆盖限制、运行事件和提供者诊断。用户可以继续调用已有独立工具，不必先进入项目工作流。

两种视图使用相同服务、身份和验收结果。界面不能通过更乐观的文案把未知项变成成功，也不能保留只有 GUI 能执行的分析或恢复逻辑。底层项目能力先经 CLI/MCP 验证。

首期技术路线规划为独立的本地 Web 工作台：Node 服务调用现有 application 层，前端采用 TypeScript、React 和 Vite。新增依赖在 PW-07 审查其版本、许可证、构建和包体影响；此处是计划选择，当前尚未安装或集成。工作台与现有 VitePress 文档站分别构建和发布，不向文档站注入运行权限；首期沿用现有程序发行方式，不增加 Electron 或 Tauri 桌面壳。

工作台服务仅绑定 loopback，由启动它的 Tekvro 进程管理生命周期。计划校验 Host、Origin 与同源会话，使用不可猜测的本次会话凭据保护项目和执行接口，并拒绝跨站写入。静态页面可访问不代表项目数据或命令接口已获授权；凭据不写入项目、日志或分享链接。监听器、浏览器端连接和仍活动的运行分别记录，关闭窗口不能被当作工作已取消。首期不提供对局域网或公网开放的工作台模式。

## 4. 分层与职责

依赖方向继续遵循[现有架构](https://github.com/ForceMind/Tekvro/blob/ee5ebf85b35c800c92d2e308ea601c158c529596/docs/architecture.mermaid)：领域语义与契约在内层，提供者和界面在边界。以下为规划职责，并非已存在的新模块或 API。

| 层                    | 规划职责                                               | 必须复用或遵守的边界                                 |
| --------------------- | ------------------------------------------------------ | ---------------------------------------------------- |
| Domain                | 项目身份、运行状态转换、要求版本、检查适用性、验收汇总 | 不执行进程、不读取文件、不认识具体编码代理协议       |
| Contracts             | 规范输入、输出、事件、项目文件 schema 和能力描述       | CLI/MCP 使用同一命名契约；不靠展示文案推断状态       |
| Application           | 项目操作、阶段编排、Evidence 与要求账本组合、恢复判断  | 调用现有分析工作流；不把提供者参数散落到业务层       |
| Storage/process ports | 项目读写、锁、原子提交、受管资源和实际执行             | 复用现有路径准入、文件所有权、取消与进程监督基础     |
| Builder adapters      | 驱动用户指定的本地编码工具或已配置入口                 | 解析其真实协议、能力和失败；不把“可发现”当作“已兼容” |
| Validators            | 用明确的场景与可验证产物执行检查并记录 Evidence        | 独立于 Builder 的成功描述，保持覆盖和权限来源        |
| CLI/MCP/UI            | 参数翻译、进度与结果展示                               | 不另写状态机、权限语义或验收算法                     |

项目工作流只组合已经有重复用途且能保留用户控制的操作。创建项目、执行明确目标、读取状态、取消或继续已有运行可能形成新的用户结果；最终工具数量与名称须先对照现有规范目录审查。不得为每个阶段增加一个只有“生成计划”效果的工具。

## 5. 项目文件与引用模型

### 5.1 存储原则

项目数据保留在用户选定的本地根目录。项目管理文件与用户代码的归属分别记录；移除项目索引不等于删除用户代码。证据和生成产物按实际需要保留，重复内容可通过摘要引用，不能复制整套原应用而不说明用途。

计划使用版本化项目 manifest，并分开保存运行记录、证据引用、要求快照、检查报告和产物索引。具体文件布局在 PW-01 冻结；下表是语义契约，不能当作当前运行包接受的输入格式。

| 记录                  | 计划保存的核心字段                                                                           | 语义                                                     |
| --------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `ProjectManifest`     | `schema`、`schema_version`、`project_id`、`revision`、创建/更新时间、`goal`、范围及记录引用  | 描述项目，不承载可执行脚本或隐藏授权                     |
| `TargetBinding`       | 调用方原始输入、实际目标身份、字节或捕获摘要、来源类型、采样时间、环境引用                   | 原始表达、解析后定位与显示名称分别保留                   |
| `RequirementSnapshot` | 范围版本、必需/可选要求、适用样例、义务 ID、证据引用、验证器约束                             | 本轮比较的固定要求集合；改变范围产生新版本               |
| `RunRecord`           | `run_id`、项目 revision、阶段、执行状态、输入/输出快照、adapter 身份、预算、检查点、终止原因 | 记录实际发生的操作，不用最后一句代理回复代替运行状态     |
| `ArtifactRef`         | 角色、路径或受管相对位置、内容摘要、表示类型、大小、生成运行、归属、可用性                   | 路径可变，内容身份不可静默替换；缺失文件仍保留引用与原因 |
| `EvidenceRef`         | 既有 Evidence ID、bundle 身份和摘要、相关来源位置                                            | 使用现有 Evidence 认证与规范结果，不创建第二套事实身份   |
| `CheckRecord`         | 检查器及版本、输入绑定、要求版本、结果、覆盖、差异、未知项、证据和产物引用                   | 同时标明检查是否执行与结论是否足够                       |

不在 manifest 内保存 API 凭据、登录材料或完整环境变量。提供者/编码工具身份应记录可复现所需的版本与配置摘要，认证值继续留在其现有所有者处。

### 5.2 证据适用性与失效

每次验收绑定目标、候选产物、要求版本、验证场景和验证器实现摘要。旧证据仍可阅读；输入代码、运行条件或必需要求改变后，不自动沿用旧的通过结论。可以复用经验证仍适用的独立检查，但须给出对应关系和未重新执行的范围。

项目引用不降低现有 Evidence 契约：摘要相同只能证明相应表示的内容身份；不能证明运行成功、跨捕获对象对应、完整性或行为等价。合成 fixture、推断结果、真实观察和打包产物各自保留原始权限与置信来源。

原始工具失败可能只有 `partial_observation` 而没有 Evidence ID。项目可以保留这种失败回执及其可用材料，但不能为其伪造 Evidence 身份或声明它已进入既有 bundle。恢复读取必须区分有身份的 Evidence、原始部分观察、已发布输出回执与资源清理记录。

### 5.3 Schema 迁移

所有持久文件都有明确 schema 和版本。迁移逐版本进行，保留源文件和迁移回执，验证后才原子替换。旧记录缺失的执行事实、权限来源或验证结果保持未知，不依据旧版文案补出成功。

读取比当前程序更新的 schema 时，只允许受控的只读展示或返回明确的不支持原因，禁止降级覆盖。迁移失败、记录损坏或缺失依赖不会触发“初始化一个空项目”覆盖旧数据。跨系统移动时重新验证路径和宿主能力；绝对路径、文件 URL 和 HTTP URL 不互相代替。

## 6. 原子提交、并发与崩溃一致性

PW-01 的元数据实现采用不可覆盖的 revision 槽协调短事务：读取完整链并比较 project_id、revision 与 digest，验证后通过既有原子文件发布独占下一序号。并发写入同一序号时返回冲突，原提交保留。完整字段、格式和当前验证见[项目存储契约](project-storage.md)。运行级互斥继续由 PW-02 实现。

CLI、MCP 和 GUI 的并发修改按 revision 检测冲突，返回最新状态和冲突字段，由调用方重新评估。不能用后写覆盖解决用户修改与 Builder 修改的冲突。读取使用已提交快照；事件序号在已提交运行内单调递增。

文件发布复用现有暂存输出与身份准入。数据先写入当前项目拥有的临时位置并读回校验，再提交引用该数据的新 manifest。对支持的文件系统记录文件/目录同步结果；网络文件系统、跨卷移动和不支持的锁语义必须明确限制，不宣称通用断电事务保证。

如果多文件写入在提交前中断，恢复只采用最后一个可验证的提交点；孤立暂存文件可报告并按所有权清理。提交成功而暂存清理失败时，保留已发布路径、摘要和发布回执，清理失败单独记录，不能重新执行整个写入而覆盖已经发布的成果。

运行级别的互斥与项目编辑锁分别处理：同一输出工作副本默认只有一个活动 Builder。并行只用于输入独立、产物互不覆盖的分析或检查；汇总时仍校验相同候选版本。未能证明旧执行已终止或失去写入能力时，不能通过删除锁文件启动第二个写入者。

## 7. 执行状态、验收状态与阶段

本节是规划中状态字段的唯一语义定义。实施计划与验收矩阵引用本节；当前公开工具不因本文新增状态字段。

### 7.1 三个不同维度

`phase` 表示当前在做哪类工作：`study`、`build`、`check`、`refine`、`deliver`。其中研究包含形成可验证要求；理解类项目可以从 `study` 进入 `check` 和 `deliver`，不经过 Builder。返修根据本轮差异修改候选，再进入下一轮 `check`。

`execution_status` 表示一次运行的生命周期：

| 值              | 含义                                     | 典型恢复条件                                         |
| --------------- | ---------------------------------------- | ---------------------------------------------------- |
| `idle`          | 运行已建立，尚未开始                     | 输入、宿主和执行范围已验证                           |
| `running`       | 正在执行当前阶段                         | 无需恢复；可以读取真实进度或请求暂停/取消            |
| `waiting_input` | 缺少改变目标或执行含义的必要输入         | 原问题有记录的回答，重新验证受影响范围               |
| `cancelling`    | 已收到取消，仍在停止与清理本次拥有的资源 | 保留部分结果，等待资源所有者给出实际结果             |
| `cancelled`     | 运行因取消而终止                         | 显式继续时创建后续 attempt，并检查历史资源回执       |
| `paused`        | 在可保存的边界暂停                       | 用户继续、有效预算增加或阻塞原因解除                 |
| `interrupted`   | 崩溃、连接丢失等导致终止事实或收尾不完整 | 重新验证检查点、产物和资源状态，禁止直接视为安全完成 |
| `succeeded`     | 本次请求的执行流程完成                   | 验收结论独立读取，可以仍是未知或失败                 |
| `failed`        | 实际执行发生不可在本次自动恢复的错误     | 按类型化原因修复后显式重试                           |

`paused` 的原因包括 `user_requested`、`budget_exhausted`、`no_progress`、`dependency_unavailable`；`interrupted` 的原因包括 `host_exit`、`agent_connection_lost`、`recovery_state_unknown`。提供者既有错误码仍原样保留在关联诊断中；这些项目原因不替换原错误分类。

`acceptance_status` 表示当前选定范围和当前候选的验收：

| 值              | 含义                                                                   |
| --------------- | ---------------------------------------------------------------------- |
| `not_evaluated` | 尚未对这组输入运行所需检查                                             |
| `pass`          | 当前必需要求均具有适用、足够且通过的证明，没有阻断该范围的矛盾或未知项 |
| `fail`          | 至少一项适用的必需要求有已观测、可复核的失败                           |
| `unknown`       | 缺证据、未执行、权限不足、不支持、截断、结果不稳定或矛盾等导致无法判定 |

可打开、已启动、可运行及已退出等 `usability` 观测另行记录来源和候选摘要。成功构建、代理宣称完成、达到迭代上限、相似度较高或点击“保留当前成果”，均不能把验收变成 `pass`。

### 7.2 汇总规则

必需要求在运行前形成版本化范围。适用的已观测失败使范围失败；其余存在阻断项时为未知；只有所有必需要求均闭合才通过。空的要求集合、未执行的检查或空错误列表不能证明成功。可选项、范围外未知与未选择的平台单独展示，不得由此宣称整个软件已验证。

理解类项目允许交付“证据已经整理，但某行为仍未知”的报告；该次执行可以成功，相关事实与受影响的验收仍保持未知。重建类项目可以交付一个能打开的部分成果，但必须保留失败/未知标记和下一步所需证据。

修改必需范围、实现或检查器后重新评估适用性。不能通过删除失败要求、放宽阈值、把必需改为可选或改变显示名称来让原有检查通过；用户明确改变目标时创建新范围版本，并保存变化原因。

## 8. 中断恢复、取消与进展预算

### 8.1 检查点与 pending check

阶段开始记录固定输入、运行身份和预计效果；阶段完成先保存产物及回执，再推进状态。Builder 已完成但检查尚未结束时保留 `pending_check`，绑定候选摘要、要求版本和待执行检查器。重启后优先补这些检查，不再次要求 Builder 生成同一项目。

恢复顺序是读取可验证的提交点、核对输入与产物、核对残留资源、确认 adapter 能力，再决定恢复会话、仅补检查或开始新 attempt。会话 ID 不等于可恢复证明；换 Agent、换宿主、改变执行范围或会话文件不存在时，使用项目事实和交接摘要继续，并明确上下文损失，不能冒充继续了原会话。

历史执行标识、PID 和可执行文件路径不能证明进程仍属本次运行。恢复不得凭旧 PID 发信号。依靠既有所有权原语重新取得充分证据，不能验证时保留 `interrupted` 与诊断，由可用工作流处理。

### 8.2 取消与清理

取消沿已有 AbortSignal 传播，停止领取后续阶段和调用 Builder。受管进程及其被证明拥有的后代、临时文件、监听器和浏览器会话由原所有者清理；用户附加的会话或外部程序不得顺带关闭。

执行主结果、已完成观察、输出发布结果与 `cleanup_status` 分别保存。`cleanup_status` 使用 `not_required`、`pending`、`complete`、`incomplete`、`unknown` 描述项目汇总事实；底层 `cleanup_incomplete` 错误和资源明细保持现有契约。清理失败不抹掉先前有效 Evidence，也不允许同一工作副本自动启动新 Builder。

客户端不再等待并不证明后台工作停止。运行必须保留终态或中断状态，使另一个 CLI/MCP 客户端能够查看实际收尾结果；恢复后继续清理与继续业务工作是两个决定。

### 8.3 无进展与失败重试

计划以选定代码和有效产物的内容身份、已完成要求及新证据判断进展。修改日志、时间戳、重复写入相同字节或重复宣称完成不算有效进展。纯研究阶段获取新证据可构成进展，不能套用只有文件变化的 Builder 标准。

连续无有效进展时进入 `paused/no_progress`，提供最后的差异、已尝试动作、未满足要求与可选择的继续条件。计数跨重启保留；点击继续但输入、方法与范围没有变化时不能自动清零。新增需求、有效修复或用户明确重新尝试产生新的 attempt，并保留前次失败史。

超时、暂时连接错误、认证失败、缺依赖、输入错误和不可恢复输出必须分别处理。仅对已证明可重试且不会重复外部效果的步骤执行有界重试；未知提交结果先查询回执，不能重新执行来猜测是否成功。

### 8.4 预算

每次自动运行有明确预算：墙钟时间、允许的返修/重试次数、输出存储，以及后端能够真实报告的 token 或费用。运行继承用户已选择的配置；启动时返回有效预算和来源。未配置自动循环预算时只执行明确的一次工作，不启动无限返修。

预算按真实度量记录。工具没有报告 token 或价格时显示未知；不能用零代替未知成本，不能把估算 API 价格当作订阅账单。要求严格金额上限但后端不能提供可执行的预算约束时，该路径不能宣称预算已受控。

达到预算后在安全边界暂停，保留成果与待检查项，不把未完成工作认定通过，也不在重启、重连或定时任务中自行恢复消耗。无进展阈值、采样次数和资源上限须依据对应实现与样例验证确定，并在机器结果中报告有效值；不把某个网站的相似度或固定轮数作为全产品质量标准。

## 9. AnalysisProvider、BuilderAdapter 与 Validator

### 9.1 三种角色

现有 [AnalysisProvider](https://github.com/ForceMind/Tekvro/blob/ee5ebf85b35c800c92d2e308ea601c158c529596/src/application/AnalysisProvider.ts) 和应用服务负责取得与解释目标事实，继续保持提供者无关契约、真实权限来源和不完整覆盖。项目层不另建一套同名分析协议，也不把新增云模型服务混入二进制提供者接口。

计划中的 `BuilderAdapter` 接收版本化的任务、限定材料、输出工作副本、适用工具入口与预算，返回真实进展、产物修改、退出信息及可恢复会话描述。它可以调用用户已经配置的编码工具；具体 CLI、ACP 或其他协议仅在 adapter 内解释。认证仍由原工具负责，Tekvro 不复制其登录凭据。

计划中的 `Validator` 读取固定候选和要求，执行现有比较或独立检查，产出绑定具体版本的结果与 Evidence。Builder 可以请求预检查并读取差异，但不能修改验收器、必需要求、通过阈值或正式检查结果来使自己通过。

### 9.2 真实能力矩阵

每个 Builder 的支持说明至少包含下列能力及验证范围，状态使用 `implemented_unverified`、`verified`、`unsupported`、`unknown`。整个 Builder 新能力在当前版本均为规划，不能填入未经 Tekvro 执行的通过记录。

| 能力               | 需要的实际证明                                                        |
| ------------------ | --------------------------------------------------------------------- |
| 可发现与可启动     | 明确本地程序身份、版本、宿主和启动结果；发现路径不算构建成功          |
| 长文本与中文输入   | 真实传递多行、Unicode 和必要长度的任务，确认没有参数截断或 shell 改写 |
| 工具访问           | Agent 实际调用本次项目绑定的 Tekvro 工具，返回正确目标与 Evidence     |
| 文件修改范围       | 说明由谁执行、哪些限制实际生效，不能把工作目录称为操作系统沙箱        |
| 图像与结构化结果   | 实际读取支持的截图或布局数据；不支持图像时明确提供结构化材料          |
| 会话恢复           | 原会话真实继续，或明确记录降级为新会话与交接摘要                      |
| 取消和进程收尾     | 真实取消下无未说明的 owned 资源残留，并保存部分成果                   |
| 用量与预算         | 区分后端实测值、估算值和未知，验证上限的实际执行行为                  |
| 中途输入与协议能力 | 实测可接收范围变更的时机、重放语义、重复请求与错误处理                |

首个计划接入目标为 **Codex CLI**，与项目当前研发使用方式保持一致。PW-03 需要固定实际可用的 CLI 版本与协议，完成真实启动、工具调用、文件修改、取消和恢复验证后，才能在对应矩阵单元标记 `verified`。缺少程序、认证或所需权限时保留受阻状态，不用另一 Agent 的结果代替。其他 adapter 在此之后逐项扩展，不因外部工具已有适配代码就宣告 Tekvro 支持。

后端切换必须由明确操作选择并记录；旧会话和旧验证结果只在明确适用时复用，不能静默换模型或执行位置。

## 10. 检查设计

### 10.1 网页与 H5 的多视口、多状态比较

同一检查同时绑定视口、设备像素比、字体环境、主题、语言、时区、测试数据、路由、用户状态和采样稳定条件。原目标与候选使用可比较的条件；差异不能通过省略失败视口或只保留最好的一张图来隐藏。

首个样例选择桌面、窄屏和触控布局的代表视口，具体尺寸在样例契约中冻结。首页、实际选定的其他页面、菜单、弹层、标签页、输入错误与空状态按必需范围采集；没有观察到的页面和操作不声称覆盖。

已有本地 PNG 比较继续使用其当前语义。结构、可访问性、字体/布局测量或新增感知指标若需要扩展，须作为明确的实现增量与相应检查；不能把当前像素比较描述成已经具备 OCR、完整感知评分或自动交互。

视觉结果分开保留每个视口和状态的指标、差异位置及完整性。按钮可操作、页面不新增错误、资源可加载、关键流程可完成等形成独立要求；视觉高分不覆盖行为失败，平均值不能隐藏必需页面的未知。

跨原站与本地重建站点进行场景对比时，两个站点的 `start_origin` 可以不同，但默认不会被认定为相同采集上下文。只有对 URL 类型显式提交、能够完整匹配其中一个源站 origin 的精确字面量归一化规则，使两个 origin 的归一化值相等，才允许对齐步骤；规则及摘要随比较结果保留。仅改写 URL 子串、只归一化操作状态、或更换浏览器产品/版本均不会绕开采集上下文保护。步骤的 URL、操作前后 URL、网络事件及其他所选数据仍要分别比较，必要时在对应数据类型显式声明规则。此能力是**已有浏览器场景比较器的纯数据边界**，不代表 M1 的真实浏览器多视口采集或完整网页验收已通过。

### 10.2 动态内容与不稳定采样

计划通过重复采样识别时间、动画、随机内容或网络变化引起的差异。每个忽略区域必须有来源、原因、区域身份和规则版本；原图和未屏蔽差异保留。Builder 不得自行增大屏蔽范围，直至差异消失。

优先使用固定样例数据、确定性随机源或现有场景控制建立稳定条件。仍不稳定时记录不可比较范围，不能把其计为相似。遮罩不能删除按钮、数值、提示或交互反馈所对应的必要义务。若范围要求这些区域的视觉一致性，被屏蔽部分仍为未知，须补充证据；若该区域预先约定只验证功能，则由独立行为证据完成对应义务，不把被屏蔽区域计入视觉通过覆盖。

### 10.3 独立行为验证

行为检查使用受控场景、明确输入与真实可观察输出：网页 DOM/可访问性状态、进程输出与退出、选定文件变化、协议记录或独立运行截图。复用已有浏览器与进程场景，不设计第二套脚本语言。

验证器及必需场景放在 Builder 不能静默改写的独立位置，校验其摘要。原目标、候选和样例依赖分别绑定身份；候选不得通过调用原应用提供的实现冒充自身行为，相关判断沿用现有重建覆盖与权限独立性规则。

游戏自行输出的“移动成功”“动作成功”或测试 JSON 只能作为一种输入。需要外部驱动或观察证据验证状态变化、计分、失败与重新开始等选定行为；不能由同一个生成程序自行给出的布尔值关闭必需玩法要求。物理手感、复杂时序或长时运行未覆盖时保持明确限制。

行为相符的声明只覆盖已执行场景与比较模型。有限轨迹、并发部分顺序、截图和协议输出不能合并成“所有运行均等价”。真实宿主不支持某种捕获时，报告对应能力未知或不可用；例如现有 Windows PTY 捕获限制仍然适用。

### 10.4 检查与返修分离

正式验收使用固定要求、独立检查器和当前候选版本。返修输入包含失败要求、差异证据、有效覆盖、未比较部分与建议补证据；不给代理一个只有总分的提示。

Builder 的中途预检查与正式检查保留不同运行身份。预检查可缩短返修过程，但不覆盖正式检查失败。候选在检查期间改变时，该轮结果对新候选失效，不能把不同版本的成功项拼成一次通过。

## 11. CLI、MCP 与机器契约

项目入口调用共享 application 服务，统一校验目标、范围、版本和效果。CLI 人类说明支持 `TEKVRO_LANG` 与中文帮助；机器字段、稳定错误码、Evidence 身份和退出语义不随语言变化，既有命令与配置兼容保持不变。

结果应直接给出当前阶段、执行/验收状态、有效预算、已产生的关键事实、适用的证据引用、未知项、输出回执和可执行恢复建议。需要完整材料时保留现有 bundle/视图能力，但不能让调用方为了理解一个结果反复查询若干 ID。

进度沿用当前进度 token 与取消契约，不虚构总步数和剩余时间。运行状态的持久化并不改变单次工具的成功/失败：类型化失败仍需正确 CLI 退出码和 MCP 错误表示，不能返回成功包裹一段失败文案。

新增工具先检查现有契约与最近似入口，按分析问题选择扩展或增加。规范 schema、SDK 转换后的 JSON Schema、工具效果元数据与生成目录必须一致。仓库生成文件的忽略规则保持不变，不把自动生成目录作为手写源提交。

## 12. 本地数据、执行范围与宿主权限

Tekvro 保持 local-only。项目文件、Evidence、采集和比较在用户选择的本地位置处理；不新增托管分析、后台上传、账号服务或遥测。报告导出不意味着对外发布，项目存续不意味着建立定时任务。

本地编码工具可能按其自身配置访问模型服务。接入该工具不等于授予上传整个目标目录的权限：执行前明确材料边界、工具能力及其已知网络行为。严格本地任务只能选用能够满足该边界的执行路径；无法建立相应事实时报告限制，不自动切换远程后端。

执行范围是实际操作契约，不是新增的通用沙箱承诺。保持当前“调用方选择目标和操作即表达请求”的规则，不新增重复授权布尔值或层层批准卡。MCP 客户端控制其确认界面；现有 setup、系统权限和工具安装规则继续生效。

保持调用方选定的输入、输出、URL、路径、摘要和分析元数据；仅处理传输认证凭据与调用方明确标为敏感的值。不得从环境变量名、参数名或文本模式猜测本地证据应被删除。继承环境与记录环境分开，不能把完整宿主环境保存进项目。

输入代码、网页文本、文件内容和 Agent 输出均作为目标材料；其中要求改变运行范围、外发文件或修改校验规则的文本不会成为项目指令。扩展范围需要来自调用方的实际操作或已记录目标变更。

安装与发行继续使用当前 Tekvro 身份、MIT 通知、`private: true`、源码更新拒绝与发布保护。项目工作流不自动安装或升级 Node、npm、Java、Ghidra 或其他软件；缺依赖通过诊断说明。npm/MCP Registry 发布不在本设计范围。

## 13. 可观测性与结果交付

事件记录至少包含项目/运行身份、事件序号、实际时间、阶段、来源、目标或产物绑定、类型化结果和耗时。模型与命令输出和领域事件分开；不要根据代理一句“已完成”制造 `succeeded` 或 `pass` 事件。

一次交付计划包含当前范围、可运行产物或分析报告、需求与实现映射、已执行检查及证据、失败/未知项、真实宿主与依赖、复现步骤和继续工作的检查点。运行原文与完整证据可以单独查看，默认摘要保留判断所需的核心材料。

项目记录的导出与机器间移动不携带可复用凭据或进程控制权。导入先校验 schema、摘要、相对路径与引用；引用到外部位置的代码不会自动复制或执行。真实支持报告须注明目标版本、宿主、工具版本、实际命令和未覆盖范围。

## 14. 实施衔接与设计完成条件

工作包与依赖以[实施计划](project-workflow-plan.md)为准，逐项通过标准以[验收矩阵](project-workflow-acceptance.md)为准。本设计覆盖 PW-01 至 PW-10；范围建立后必须保持产品文档、机器契约和实际行为一致。

PW-01 先冻结项目 schema、状态转换、要求/证据适用性、输出归属与并发规则，再验证其持久化实现。进入对应真实闭环验收前，Codex CLI adapter 和网页/H5 样例须具备可执行验证条件；缺少 Agent 的机器仍可独立推进项目存储、契约和检查器工作，并如实保留 Agent 验收受阻状态。已有工具能完成的部分通过组合使用，新代码只填补已确认的缺口。

项目层验收至少证明：两种入口恢复同一项目；中断只补待执行检查；取消保留部分事实并报告清理；并发写入不会覆盖成果；旧证明不能通过新产物；未知、缺图或行为失败不能得到验收通过；真实编码工具完成一次可复核闭环；没有新增未经请求的数据外发或发行通道。

完成文档不计为上述能力完成。测试替身与合成报告只建立各自契约；平台支持、实际代理适配、预算执行、进程清理和软件行为声明必须由对应真实路径建立。
